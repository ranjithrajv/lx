# Outreach

Material aimed at upstream maintainers and communities: take a real,
specific packaging pain point — usually a blog post, issue, or thread
from someone who ships Linux software — and show concretely what `lx`
does about it.

These are written to be publishable as-is and linkable from an issue, a
reply, or a PR. They are not marketing copy: each post states what `lx`
does **not** solve as plainly as what it does.

## Ground rules

- Start from the other person's stated problem, in their words, before
  mentioning `lx`.
- Every claim maps to a command, a config field, or a doc in this repo.
  No feature is implied that is not implemented.
- Name the gaps. A post that only lists wins is not credible, and not
  useful to the person deciding whether to adopt the tool.
- Prefer "here is the exact `lx build` line for your repo" over a feature
  matrix.
