# `lpt scan-deps`: native ELF shared-library dependency scanning

**Date:** 2026-08-20
**Context:** Asked directly to add a CLI command for "dependency scanning" -- ambiguous enough (could mean scanning packaged binaries' runtime deps, or scanning `lpt`'s own Rust dependencies for CVEs) that it was worth checking rather than guessing; confirmed the former, which extends directly from this session's packaging-fidelity and trust/audit work. `package.yaml`'s `depends:` field (added earlier this session, see `2026-08-20-nfpm-adoptions.md`) has always required manually knowing a binary's runtime library needs; nothing in `lpt` could tell you what they actually are.

## What it does

`lpt scan-deps [config]` resolves a release the same way `lpt build` does (config file or a bare GitHub URL, version pinning, manual or auto-discovered architecture patterns), downloads the binary for one or more architectures, extracts it, and reports every ELF binary's `DT_NEEDED` entries -- the same information `ldd`/`readelf -d` show. Each soname is annotated:
- **essential** (glibc/`libc6`, `Priority: required`, always present) -- listed but flagged as usually omit-able from `depends:`, matching Debian/`dpkg-shlibdeps` convention;
- **resolved via local `dpkg -S`** when `dpkg` is on `PATH` and the library happens to be installed on this host -- a real fact about this machine, not a guess, and clearly labeled as such;
- otherwise listed bare, for the user to cross-reference themselves.

Defaults to scanning just this machine's own architecture (`--host`-equivalent, via the same `host_arch()` used by `build --host`); `--architectures`/`--all-architectures` widen it.

## Library choice: `object` crate, not `ldd`/`objdump`/`readelf`

Followed `/foss-mind` before writing anything, then re-ran the evaluation with harder data after an initial pass leaned too much on a summarized web search rather than checked facts. Candidates: `object` (gimli-rs) vs `goblin` (m4b/goblin). Both MSRV 1.85 (matches this project's floor exactly), both 100% API fit (`Object::import_libraries()` is documented explicitly as "for ELF, this corresponds to `DT_NEEDED` entries" -- no adaptation needed), both clean on RustSec advisory-db and OSV.dev (no known CVEs).

Scored under the "long-lived / core dependency" context (min 70, Maintenance and Ecosystem health weighted x2), using real commit-history and dependency-graph data rather than downloads/stars alone:
- **Bus factor, checked against the actual last 100 commits, not assumed from org affiliation**: `object` is 93% one author (Philip Craig) despite being nominally a multi-maintainer `gimli-rs`-org repo; `goblin` is more distributed in practice (m4b 35%, a second contributor 25%, eight more distinct names in the remainder) despite being a single-named-maintainer project on paper. The naive "org repo = more bus factor" assumption from the first pass didn't hold up -- this axis is close to a wash, if anything a slight edge to `goblin`.
- **Dependency chain**: `object` has one direct dependency (`memchr`, BurntSushi, independently and famously well-maintained). `goblin` has two (`plain`, `scroll`) -- both *also* maintained by `goblin`'s own author, meaning a single person's departure would simultaneously affect three crates in the chain, not one. This is the axis that actually favors `object`, and more concretely than the original "ecosystem entrenchment" framing suggested.
- **License**: `object` is dual Apache-2.0/MIT (explicit patent grant); `goblin` is MIT-only. Per this project's license-evaluation rubric, Apache-2.0 is preferred over MIT specifically for the patent grant -- a real, if minor, edge to `object`.

Net: `object` still wins (weighted score ~90/100 vs. `goblin`'s ~84/100), but for the dependency-chain and license reasons above, not primarily "ecosystem health" as first claimed -- that axis alone doesn't clearly favor either crate once actually checked. Both cleared the threshold comfortably; this wasn't a close call on validity, just a correction to *why*.

Deliberately not shelling out to `ldd`/`objdump`/`readelf`: unlike `lintian` (a large Debian-native Perl static analyzer with no reasonable Rust port), ELF DT_NEEDED parsing is a narrow, well-understood format with mature pure-Rust parsers already available -- there was no reason to reach for a host tool and reintroduce the kind of dependency this project spent the rest of the session removing.

## Scope decisions

- **No checksum verification on the download.** Every other download path in `lpt` (`build`, `install`, `upgrade`) now fails closed without a pinned or sidecar checksum (see `2026-08-20-package-request-audit.md`), because those downloads become installed, trusted system state. `scan-deps` downloads a binary purely to inspect its bytes locally and discards it -- nothing is built, installed, or trusted onto the system, so the risk model that motivated fail-closed verification elsewhere doesn't apply here. Disclosed explicitly in the command's own output (`"downloading (unverified -- inspected locally only, never installed)"`) rather than silently differing from the rest of the tool.
- **No automatic soname → Debian package name guessing.** The obvious "helpful" next step -- stripping `lib`/`.so.N` and guessing a package name (`libssl.so.3` → `libssl3`) -- was deliberately rejected: it works for some sonames and is flatly wrong for others (`libz.so.1` is `zlib1g`, not `libz1`), and a wrong guess presented with the same confidence as a real fact is worse than no guess at all. `dpkg -S` gives a real, verifiable local fact instead of a heuristic; when it's unavailable (non-Debian host, library not installed locally) the soname is shown bare rather than backed by a fabricated answer.
- **No fuzzy matching against the config's existing `depends:`.** Considered auto-flagging sonames "missing" from `depends:` by substring-matching against the field's text, but a soname and a Debian package name aren't reliably related strings (see above) -- would produce false "missing" flags as often as real ones. Instead just prints the resolved sonames and the config's current `depends:` value side by side for the user to judge.

## Verification

- New tests: `lib/elfdeps.rs`'s `rejects_non_elf_input`, `essential_libc_sonames_are_recognized`, and `real_dynamically_linked_binary_reports_libc` (reads this host's real `/bin/ls`, skips gracefully if absent or statically linked -- mirrors `debarchive.rs`'s `real_dpkg_deb_accepts_the_archive` skip pattern); `src/scandeps.rs`'s `find_elf_files_walks_nested_dirs_and_skips_non_elf`, `dpkg_owner_is_none_when_dpkg_unavailable_or_no_match`, and `raw_format_extraction_preserves_the_real_asset_name` (regression, see below).
- **Live, not just unit-tested**: ran `lpt scan-deps https://github.com/eza-community/eza --architectures amd64` against the real release -- correctly reported `eza`'s five glibc-essential sonames plus one genuine non-essential dependency (`libgcc_s.so.1`, from `libgcc-s1` -- a real, correct finding, not noise). Ran with `--all-architectures` against a config pinning only amd64/arm64 and confirmed a third architecture (armhf) was still scanned via `resolve_manual`'s existing auto-discovery fallback for unpinned archs -- expected, pre-existing `build.rs` behavior, not new. Confirmed the default (no `--architectures` flag) scans only the host's own architecture, and that an unavailable architecture fails with a clear message instead of a panic or silent no-op.
- **Follow-on validation pass (2026-08-21) found and fixed one real bug**: scanning `neovim/neovim`'s real `nightly` AppImage release (a `raw`-format asset, auto-guessed since `.appimage` isn't a recognized archive extension) displayed the binary as `amd64-nvim-linux-x86_64.appimage` instead of `nvim-linux-x86_64.appimage`. Root cause: `scan-deps` downloaded each architecture's asset into a *shared* temp dir disambiguated by prefixing the on-disk filename with the arch (`"{arch}-{asset_name}"`), to avoid same-named assets colliding across architectures -- but `build::extract`'s `"raw"` branch names the extracted file after the *downloaded file's own on-disk name* (correct for `build.rs`'s own single-download-per-job use, since it never added a prefix there), so the disambiguation prefix leaked into the displayed result for any `raw`-format asset specifically. Fixed by downloading into a per-architecture *subdirectory* instead of a prefixed filename, preserving the asset's real name through extraction. Tar/zip-format assets were never affected (their extracted members keep their own internal archive paths, independent of the downloaded archive's on-disk name) -- confirmed via the earlier `eza`/`ripgrep` live runs, both `tar.gz`, showing clean names throughout.
- Also exercised, same follow-on pass: the prerelease/draft warning firing correctly inside `scan-deps` (via `neovim/neovim`'s real `nightly` tag, same mechanism as `build`/`validate`); the `dpkg -S` resolution annotation actually rendering (`libgcc_s.so.1  -> libgcc-s1 (via local dpkg -S)`), using a fake `dpkg` shim on `PATH` since this dev machine has no real `dpkg` -- the same shim technique used earlier in the session to prove `lintian`'s host-first dispatch; and a real 23-binary bundle-mode release (`zed-industries/zed`'s `zed.app/{bin,libexec,lib}` tree, `bundle: true`), confirming `find_elf_files`'s recursion and the deduplicated cross-binary summary hold up at scale (finished in ~21s, no crash, correct dedup down to 22 unique non-essential sonames across 23 scanned ELF files).
- Full suite: 108 tests (49 lib + 59 bin) pass; `cargo fmt --all -- --check`, `cargo clippy --all-targets --all-features -- -D warnings`, and the full pre-push hook tier (coverage gate, `cargo audit` on the new `object` dependency) all clean.

## Known limitations, disclosed rather than silently accepted

- Only reports **direct** `DT_NEEDED` entries, not the transitive closure (a needed library's own dependencies) -- matching what `ldd -u`/a single `readelf -d` pass would show, not a full `ldd` recursive resolution. Sufficient for filling in `depends:` (Debian's own dependency resolution handles transitive closure via the target library packages' own `Depends:`), but disclosed here rather than implied to be exhaustive.
- `dpkg -S` resolution reflects *this build/dev machine's* locally installed package set, not the target Debian suite/architecture being packaged for -- a soname resolved here may be provided by a different package version (or not be installed at all) on the actual target system. Labeled "(via local dpkg -S)" in the output specifically so this isn't mistaken for an authoritative cross-distro answer.
